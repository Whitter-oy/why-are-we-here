# Why Are We Here?

## Learning to Judge, Not Just to Write

I came to this course with almost no programming experience. My background is mainly in user experience and digital product design, where I usually work with user research, interfaces, prototypes, and visual systems. At first, the obvious question was: if AI can already generate working code from a prompt, why should a designer like me still spend time learning programming?

After the first two weeks, I think the answer is not that I need to become better at writing code than AI. What I need is enough understanding to describe what I actually want, read what the machine gives me, and judge whether the result is correct. In that sense, programming is becoming less about typing every line myself and more about developing judgement.

One exercise in Week 2 made this very clear to me. We were given several Python programs that all ran successfully but produced the wrong result. One calculated an average using the wrong number of values. Another created a 3 × 5 grid, but changing one row unexpectedly changed all three rows. A third produced eleven opacity steps when the brief asked for ten. None of these programs crashed. The computer was perfectly happy with them.

Before this exercise, I tended to think that if code ran without an error, it was probably correct. I now understand that these are completely different questions. A program can be syntactically valid and still fail the brief. This matters even more when working with AI-generated code, because AI can produce something that looks convincing very quickly. If I cannot read the logic or test the result against a specification, I can only accept what the system gives me.

## From a Prompt to a Specification

This also changes how I think about prompting AI. In design, it is easy to say something like “make an interactive experience that feels playful” or “generate a chaotic visual.” But those descriptions leave many decisions undefined. How chaotic? What stays fixed? What can move? What should happen when the user interacts?

The Schotter exercise gave me a simple example. The visual idea of “order gradually becoming disorder” sounds easy to describe, but the code has to turn that idea into measurable rules. The top row stays fixed, the amount of damage increases with each row, and rotation and displacement are limited by specific values. Once these rules are written down, the vague design intention becomes something that can actually be tested.

I chose this course because my background is mainly in user experience and digital product design, and I have very little experience with programming. As AI tools become increasingly involved in design and creative work, I think understanding code is becoming more important for designers. I do not expect to become a professional programmer, but I want to understand how code works, how to communicate with AI-generated code, and how to judge whether a program actually does what I want it to do.


## What I Want to Learn

I want to learn the basic logic of programming and become more comfortable reading and modifying code. I also want to understand how programming can be used in interactive design, generative art, games, and AI-related creative projects.

## How Programming Relates to My Design Practice

As a designer, I usually focus on user experience, interfaces, and prototypes. Programming can help me understand how these ideas are implemented and allow me to create more interactive prototypes instead of only designing static interfaces.
